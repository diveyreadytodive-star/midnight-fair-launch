# Browser wallet integration preflight — 2026-09-27

Status: **integration spike only; no user-signed transaction**.

The DApp Connector v4 package declares `getDustBalance()` as `{ cap, balance }`. The public read-only wallet panel previously treated the whole response as a bigint, so a conforming wallet would show DUST as unavailable. It now extracts and validates `balance`; a v4-shaped response is covered by a regression test.

The version-matched official fetch-ZK and DApp Connector proof packages plus the official example's Vite/WASM build path were installed. The failing top-level-await plugin was removed because current Chrome supports native top-level await and the library build failed in its SWC transform. Vite was upgraded to a patched 7.3.6; `npm audit` then reported zero vulnerabilities. The `src/browser/fair-launch-client.ts` spike first built only to ignored `.local/browser-build`; its **read-only chain-query bundle** was later published on Pages and verified separately in the [public HTTPS readback](preprod-browser-readback-2026-09-27.md). Its write methods are not connected to public controls.

A temporary same-origin page served at `127.0.0.1:3083` loaded the bundle in Codex In-app Browser. With a deliberately fake API object, it queried the real Preprod indexer for an all-zero nonexistent address and displayed `Contract was not found on the wallet network`. This establishes module/WASM loading and public query reachability from a browser, not proof generation, wallet balance, signature, transaction submission, or a deployed Fair Launch contract. The temporary page and server were removed/stopped after the check.

The [Preprod contract is now funded and independently verified](preprod-launch-2026-09-27.md). Before enabling a public transaction control, the spike still needs publicly hosted matching ZK artifacts, real compatible Lace/1AM testing, durable opening and payment-coin recovery, and a user-signed receipt with contract/wallet readback. A fresh Chrome tab opened the public site; its wallet panel detected no compatible API v4 Lace/1AM provider. No extension prompt was tested. The browser client includes **unverified** test-payment mint and registration call paths, but no public write control, settlement, or claim flow. Source code alone must not be described as a working bid.

An isolated PBKDF2-SHA256/AES-256-GCM recovery helper now encrypts the opening and exact payment coin record into a passphrase-protected JSON backup. It authenticates contract, wallet public key, and slot as associated data. Wrong passphrase, wrong wallet, and modified header were rejected in tests; a temporary same-origin browser page also completed an encrypt/decrypt round trip. This helper is **not wired to a bid form or operator handoff**. It does not yet make any live deposit safe to accept or recover after a page close.

The `stage:browser-artifacts` command copied only the locally compiled `mintTestPaymentCoin` and `registerBid` prover/verifier/bzkir sets into ignored `.local/browser-build/zk` and wrote a SHA-256 manifest. A temporary local browser page used the official `FetchZkConfigProvider` to load both complete sets: mint prover 5,204,685 bytes and bid prover 19,476,785 bytes. The browser-computed SHA-256 digests of all six fetched files matched the local compile manifest. This initial check verified local browser retrieval and byte identity, **not** extension proving or a transaction. The files were subsequently [hosted and verified on public HTTPS](public-zk-assets-2026-09-27.md), still without a wallet proof.
