# Fair Launch 제품 흐름 — Explore → Create → 경매 상세

작성: 2026-09-26 · 상태: Explore/Create/상세 화면과 Local Devnet 운영자 서명 Create 검증. 사용자 지갑 거래는 미구현

## 사용자가 기대하는 런치패드

첫 화면은 하나의 입찰 폼이 아니라 **출시된 토큰을 찾는 Explore**다. 상단의 `Create`에서 사용자가 이름·티커·이미지·설명과 판매 조건을 정하고 출시한다. Explore의 카드를 누르면 해당 토큰의 상세 페이지로 이동해 규칙을 확인하고 봉인 입찰에 참여한다.

```text
Explore (검색·실제 출시 목록)
  ├─ Create / Launch → 설정 → 지갑 서명 → 배포·발행·재고 예치 → 목록 등록
  └─ 토큰 카드 → 토큰 상세 → 봉인 입찰 → 동일가격 정산 → 토큰/환불 청구
```

카드의 상태는 `입찰 예정`, `입찰 중`, `정산 중`, `정산 완료`, `취소`를 사용한다. **본딩커브와 DEX 거래가 없으므로 `Graduated`, 시가총액, FDV, 현재 거래 가격은 표시하지 않는다.**

## Create가 실제 기능이 되려면

창작자가 입력하는 `name`, `symbol`, 이미지 URL·설명, 경매 판매량, 최저 단가, 공통 예치액, 입찰 시간`은 배포 전에 확정·공개돼야 한다. 현재 MVP는 별도 창작자 물량·락업·유동성 옵션을 지원하지 않는다. 새 출시에서는 이 메타데이터와 설정의 해시를 계약의 공개 `networkDomain`에 묶는다. 이미지 URL 문자열이 고정될 뿐 해당 URL의 원격 이미지 바이트가 고정되는 것은 아니다.

1. 창작자 지갑이 새 경매 계약을 배포한다. 계약 주소가 그 출시의 고유 ID가 된다.
2. 출시 토큰을 한 번만 발행하고, 사전 정한 판매 재고를 해당 경매 계약에 예치한다.
3. 공개된 메타데이터 해시와 계약 상태·발행/예치 거래가 일치하는지 확인한 뒤 Explore에 등록한다.
4. 목록의 `입찰 중` 여부는 서버가 임의로 정하는 값이 아니라 계약의 시간·상태와 대조한다.
5. 마감 후 정산과 각자의 청구는 기존 4인 봉인 경매 회로를 재사용한다.

현재 Fair Launch 계약은 **한 계약 인스턴스당 고유한 테스트 토큰과 경매**를 만든다. Local Devnet Create 실행기는 새 설정의 계약 배포·1회 발행·재고 예치 3개 거래와 원장 상태를 확인한 뒤 중앙 카탈로그에 추가한다. `Midnight Moth Test`는 CLI로, `Night Bloom Test`는 브라우저 Create 버튼으로 실제 생성했다. **두 경우 모두 서버의 운영자 테스트 지갑이 서명했다.** 임의 사용자의 지갑이 직접 서명하는 permissionless 발행은 아직 아니다.

## Explore의 진실 원천

Explore의 [카탈로그](../web/fair-launch-catalog.json)에는 서로 다른 계약 주소 세 개가 있다. 첫 `Unlabeled test token`은 [20건의 Local Devnet 거래 증거](../spikes/fair-launch/docs/evidence/local-devnet-fair-launch.json)에 대응하지만 당시 메타데이터가 계약에 묶이지 않아 이름·티커를 비워 두었다. 뒤의 두 출시는 각각 배포·발행·예치 영수증과 원장의 메타데이터 해시·재고를 확인했다. **카탈로그 운영자는 중앙 서버**이며, 파일에 임의 항목을 추가하는 것만으로 검증된 출시가 되지는 않는다.

실제 다중 출시 버전은 각 목록 항목에 `contractAddress`, `creator`, `metadataHash`, `saleTokenType`, `inventory`, `reservePrice`, `depositLot`, `commitDeadline`, `openDeadline`, `status`, `deploy/fund receipt`를 결합한다. 메타데이터 원본은 공개 저장소/스토리지에 둘 수 있지만 계약의 해시와 일치해야 한다. 검증되지 않은 항목은 목록에 올리지 않는다. 중앙 카탈로그로 시작한다면 그 운영자를 명시하고, 나중에 온체인 registry 또는 계약 코드 해시 기반 인덱싱으로 바꿀 수 있다.

## 현재 구현과 다음 기술 관문

| 흐름 | 현재 상태 | 실제 완료 조건 |
|---|---|---|
| Explore | 검증된 계약 3개를 검색·필터·상세 이동. 정적 공개 사이트에서는 기록된 카탈로그를 읽음 | 공개 네트워크에서 새 출시를 검증해 자동 인덱싱 |
| Create | Local Devnet 운영자 서명 방식으로 브라우저 버튼→배포·발행·예치→목록 추가까지 검증 | 임의 사용자의 지갑이 직접 서명하는 발행 |
| 토큰 상세 | 선택한 계약의 설정과 증거를 읽음. 원래 4인 계약에서 정산·청구 Local Devnet 완료 | 각 사용자의 브라우저 지갑으로 봉인 입찰·토큰/환불 청구 |
| 유동성·거래 | 미구현 | 실제 준비금과 본딩커브/DEX 거래 검증 전까지 `Graduated` 금지 |

**다중 출시 통합 검증은 완료했다.** 이름·티커·재고·최저가격이 다른 두 새 설정이 각각 별도 계약 주소와 토큰 타입으로 발행됐고, 원래 경매 계약의 결과를 바꾸지 않은 채 Explore에 표시된다. 다음 큰 기술 관문은 창작자 지갑의 브라우저 서명과 사용자의 봉인 입찰·청구다. 운영자 서버가 대신 서명하는 현재 시험 기능은 `permissionless user launch`로 부르지 않는다.

브라우저에서 사용자가 계약을 직접 배포하는 패턴은 [Midnight의 공식 Leaderboard DApp 예제](https://docs.midnightkorea.org/examples/dapps/leaderboard)에 있다. 이 제품에도 같은 지갑 권한·증명·제출 경계가 필요하며, 현재 정적 Fair Launch 페이지에는 아직 연결되지 않았다.
