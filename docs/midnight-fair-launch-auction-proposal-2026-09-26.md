# Midnight Fair Launch — 봉인 경매 제안서와 본딩커브 확장 설계

작성: 2026-09-26 · 상태: **설계안 + 가치 없는 Local Devnet 4인 MVP 검증. 본딩커브·브라우저 거래는 미구현**

**구현 업데이트:** [Fair Launch 계약과 실행 안내](../spikes/fair-launch/README.md)의 고정 4인 경매가 실제 Local Devnet에서 배포·4건 입찰·동일가격 정산·4건 환불·2건 판매대금 청구·2건 토큰 청구까지 완료됐다. [20개 거래 영수증](../spikes/fair-launch/docs/evidence/local-devnet-fair-launch.json)을 인덱서에서 재조회했고, 각 지갑 잔고를 확인했다. 청산가격 10, 배정 `300/300/0/0`, 환불 `2,000/2,000/5,000/5,000`, 판매자 대금 6,000이다. 저장소 전체 테스트는 79/79 통과했다. 이는 **한 가지 Local Devnet 실행 사례**이며, 웹 화면은 아직 읽기 전용이고 원시 거래 프라이버시 감사도 완료되지 않았다.

## 0. 한 문장과 판정

새 밈코인과 첫 판매 물량을 미리 고정한다. 구매자는 정해진 기간 동안 최대 지불 의사와 희망 수량을 비공개로 제출한다. **모든 유효 입찰을 포함해 일괄 배정·동일가격 정산·토큰 청구·환불**을 실제로 실행하고 검증한다. 먼저 본 사람이 싸게 사는 초기 선착순 판매를 봉인된 가격 발견으로 바꾸는 Midnight 기반 출시 방식이다.

**이번 해커톤 제출 범위:** 가치 없는 고정 테스트 밈토큰 1종, 결제용 테스트 자산 1종, 최대 4명, 한 번의 봉인 경매, 실제 Local Devnet 정산과 각 지갑의 토큰·환불 청구. 창작자용 범용 토큰 생성, 본딩커브 매수·매도, DEX 유동성·LP 락, 사람당 1회 증명은 **구현·검증 전까지 제출 기능으로 표시하지 않는다.** 30분은 제품 설정값이며 짧은 데모 시간으로 바꾸더라도 같은 마감 규칙을 사용한다.

**후속 제품 비전:** 검증된 경매 청산가격을 실제 준비금에 맞춘 공개 본딩커브의 시작 상태로 연결한다. 이는 차별화 방향이지만 이번 제출의 완료 조건은 아니다. 커브가 없다면 경매 후 2차 거래까지 제공하는 런치패드라고 부르지 않는다.

가장 중요한 설계 판단: **팁을 많이 낸 순서대로 싼 커브 구간을 긁는 구조는 기본 Fair Launch에서 제외**한다. 이는 번들의 속도 우위를 경매로 팔아 되돌릴 수 있지만, 자본이 앞자리의 할인까지 사는 방식이다. 별도의 `Priority Launch` 실험으로는 흥미롭다. 기본 제품은 가격 입찰에 따라 배정하되 낙찰자 모두에게 같은 청산가격을 적용하는 `Sealed Batch Launch`가 낫다.

이 제안서의 금액·토큰 수량은 **정수 단위 예시**다. 실제 배포 때는 토큰 decimals, 최소 단위, 반올림, 수수료, 증명 비용을 별도로 고정·검증해야 한다. `TEST`는 가치 없는 테스트 결제 자산으로 가정한다.

## 2. 제품 약속과 비약속

**약속할 수 있는 목표**

1. 창작자가 판매·팀·유동성 물량과 규칙을 입찰 전에 바꿀 수 없게 한다.
2. 블록 포함 순서나 거래 전송 속도가 경매 배정과 가격에 영향을 주지 않는다.
3. 공개 관찰자는 입찰 원문을 읽지 못하지만, 등록된 입찰이 빠짐없이 같은 규칙으로 처리되고 지급+환불 합계가 맞는지 검증한다.
4. 정산 후 발행 토큰이 실제 각 낙찰자 지갑에 들어오고, 미사용 결제 자산이 청구 가능하다.
5. 후속 제품에서만 공개 커브의 첫 가격과 실제 준비금이 경매 결과에 수학적으로 연결된다.

**약속해서는 안 되는 것**

- `개발자의 모든 차명 지갑 매수를 차단`: 지갑당 제한만으로는 불가능하다. 사람당 한도가 필요하면 독립 자격 발급자의 중복 방지 credential이 필요하고 그 발급자를 신뢰한다.
- `MEV 완전 제거`, `누구나 같은 수익`, `화제성을 정확히 맞힌 사람만 수익`: 규칙만 보장할 수 있다. 출시 후 가격은 상승·하락할 수 있다.
- `완전 익명`: 입찰 시각·등록 수·고정 예치·청구 때의 수취인 공개 경계가 남을 수 있다. 원시 거래 프라이버시 감사 전에는 입찰 값의 공개 상태만 주장한다.
- `운영자도 입찰을 모름`: 첫 버전에서 정산 prover가 마감 후 모든 유효 입찰 원문을 받는다면 운영자는 이를 안다. 운영자에게도 숨기는 설계는 별도의 다자 계산/암호화와 신뢰 분석이 필요하다.
- `러그 불가`: 계약상의 공급·LP 인출은 제한할 수 있어도 허위 홍보, 차명 매수, 출시 후 시장 매도는 완전히 막지 못한다.

## 3. 기본 경매: Sealed Batch Launch

### 3.1 창작자 생성·사전 약속

전체 제품에서는 창작자가 `name`, `symbol`, 이미지/설명/링크의 콘텐츠 해시, 총공급량 `S_total`, 경매 판매량 `S_auction`, 커브/LP 재고 `S_curve`, 팀 몫 `S_team`, 팀 vesting, 결제 자산, 기준가격 `p_floor`, 경매 시작·종료 시각, 판매 성립 최소 조건, 참가 한도, 수수료, 정산 실패 시 환불 기한을 확정한다. `S_total = S_auction + S_curve + S_team + 기타 공개 몫`이 검증돼야 한다. **해커톤 MVP는 고정된 테스트 토큰과 사전 확정된 경매 재고만 사용한다.** 커브·팀 물량·vesting을 실제 구현한 것처럼 보이지 않게 한다. 토큰은 한 번만 발행해 경매 계약이 판매 물량을 보관하며, 창작자가 임의 민팅하거나 판매 물량을 바꾸는 경로를 두지 않는다. 현 VeilIntent의 테스트용 누구나 호출 가능한 `mintTestCoin` 회로를 생산용 토큰 발행 권한으로 재사용하면 안 된다.

상품 화면에는 토큰 주소, 이미지·설명 해시, 실제 경매 물량, 결제 자산, 가격 공식, 환불 경로를 입찰 전에 보여준다. 추가 발행·창작자 물량·유동성 권한이 존재한다면 이를 숨기지 않고 표시한다. 메타데이터를 나중에 바꿀 수 있다면 변경 이력/권한이 보이게 해야 한다.

### 3.2 등록과 30분 봉인 입찰

입찰 `i`의 논리값은 `b_i = (auctionId, maxUnitPrice p_i, desiredQuantity q_i, deposit d_i, recipient, nonce, salt)`다. 공개 ledger에는 이를 도메인 분리한 commitment, 중복 방지 키, 등록 카운트/루트, 경매 시간만 둔다. `p_i`, `q_i`, `recipient`의 공개 여부는 별도 원시 거래 검사로 확정한다. `p_i >= p_floor`, `q_i <= q_cap`, `d_i >= p_i·q_i`를 검증한다.

**입찰 예치액이 가변으로 공개되면 `p_i·q_i`의 상한이 새어 나간다.** 해커톤 최소 버전은 참가자당 같은 공개 예치 lot `D`와 동일 최대 구매 묶음 `q_max`를 택하거나, 예치 자체의 비공개성을 원시 거래 수준에서 따로 검증해야 한다. 공통 lot을 쓰면 `p_i·q_i <= D`이고 높은 최대가격의 입찰에는 예치 한도가 된다. 참가자는 입찰 전 토큰 정보와 일정을 알아야 하므로 등록을 경매 직전에만 열지 않고 사전 공지한다.

중복 방지는 `wallet` 기준과 `사람/자격` 기준을 구분한다. 전자는 여러 지갑에 약하다. 후자는 발급된 익명 credential에서 경매별 nullifier를 만들되 자격 발급·취소·창작자 제외에 신뢰 가정이 있다. MVP가 지갑 기준이라면 `봇 방지/개발자 차명 매수 방지`라고 쓰지 않는다.

### 3.3 마감·정산 함수

마감 후 유효 입찰을 단가 `p_i` 내림차순으로 정렬한다. 판매 물량 `S_auction`을 채울 때까지 수량을 배정한다. `p_clear`는 **최저 낙찰 단가**이고, 총 유효 수요가 판매량보다 작으면 미리 공지한 `p_floor`다. `p_clear` 단가의 총 수요가 남은 물량보다 크면 해당 그룹에 비례 배정한다. 타임스탬프/거래 순서를 동점 우선권으로 쓰지 않는다.

각 참가자에게 `0 <= allocation_i <= q_i`, `charge_i = p_clear·allocation_i`, `refund_i = d_i − charge_i`다. 다음을 증명해야 한다.

```text
Σ allocation_i <= S_auction
Σ charge_i + Σ refund_i = Σ d_i
모든 낙찰자: p_i >= p_clear
모든 미낙찰자: 더 높은 입찰에 물량이 소진되었거나 경매 성립 조건 미달
마감 시 확정된 모든 유효 commitment가 정확히 한 번 포함
```

비례 배정의 정수 반올림: 경계가격 그룹의 총 수요를 `Q_t`, 남은 물량을 `R`이라 할 때 우선 `floor(R·q_i/Q_t)`를 부여한다. 남은 최소 토큰 단위는 나머지 `R·q_i mod Q_t`가 큰 입찰부터 한 단위씩 준다. 완전 동률의 순서는 입찰 시각이 아니라 사전에 정한 commitment 해시 순서로 결정한다. 커밋해시 선호도를 노리고 salt를 반복 생성하는 공격 가능성이 있으므로 동률이 잦다면 이 마지막 규칙을 공개 랜덤 시드/VRF로 교체해야 한다. 해커톤 예시는 나눠떨어지는 수량으로 먼저 구현한다.

```text
snapshot = 마감 시 등록된 commitment 전부
각 commitment → 유효한 opening 1개; 하나라도 opening이 없으면 정산 전체 취소
유효한 입찰을 p 내림차순으로 묶음
각 가격 묶음에서 잔여 판매량보다 수요가 작거나 같으면 전량 배정
처음 초과하는 경계가격 묶음은 비례 배정 후 중단
전량 판매면 p_clear = 마지막으로 배정된 가격
미달 판매면 p_clear = 사전 공개한 p_floor
판매량·모금액·참여자 수 최소 조건 미달이면 경매 취소·전액 환불
성립하면 각자의 charge=p_clear×allocation, refund=deposit−charge
```

미공개 commitment를 몰래 목록에서 삭제해서는 안 된다. **MVP의 단순한 안전 규칙은 opening이 하나라도 없거나 commitment와 맞지 않으면 전체 경매를 취소하고 전액 환불하는 것**이다. 접수 시 유효성 검사를 통과하지 못한 입찰은 등록 자체를 거절한다. 이 규칙은 운영자의 선택적 제외를 막는 대신 한 참가자의 비협조로 경매 전체가 취소될 수 있다는 가용성 문제를 낳는다. 입찰 시 opening을 정산자에게 암호화해 전달하거나 미공개 입찰에 불이익을 주는 개선은 별도로 설계해야 한다. 숨긴 `p_i/q_i` 값을 계속 비공개로 두면서 이 전체 계산을 검증할 수 있는지가 **가장 어려운 증명 과제**다.

**완전성의 어려움:** Merkle root 하나만 저장하고 정산 prover가 자신에게 유리한 입찰만 가져오면 안 된다. MVP는 **최대 4명**, 고정 길이 전체 commitment 목록과 등록 수를 증명 입력에 묶고 전원 포함을 검증한다. `bidRoot`, `bidCount`, 정산 결과 commitment를 쓰더라도 이 세 값의 존재만으로 포함 증명이 완성되는 것은 아니다. 대규모 입찰의 정렬·포함 증명 확장은 후속 연구이며 Compact 회로 비용/블록 한도를 반드시 실제 측정한다. 마감 후 입찰 opening을 prover에게 전달하는 방식에서는 운영자가 값을 아는 신뢰 경계가 있다. 운영자/입찰자 미협조 시 정산 기한 이후 전액 환불 경로가 필요하다.

### 3.4 청구·성립 실패

정산 트랜잭션 `settleBatch`는 각 등록 입찰의 배정량·청구 가능 환불액을 한 번만 확정한다. 이후 참가자는 자신의 비밀과 commitment opening으로 `claimTokens`와 `claimRefund`를 **자기 지갑에서 별도 청구**한다. 같은 권리를 두 번 청구하거나 다른 수취인이 청구하는 경로는 거절한다. 현재 Compact 표준 `sendShielded`는 타 사용자 지갑에 보내도 수취 알림 ciphertext를 자동 생성하지 않는다고 명시하므로, VeilIntent에서 검증한 각 수취인 자기 청구 패턴이 재사용 후보이다. 두 자산의 실제 청구/지갑 readback은 새로 검증해야 한다. [Midnight 표준 라이브러리](https://docs.midnight.network/compact/standard-library/exports#sendshielded)

유효 입찰 0건, 최저 성립 조건 미달, 정산 증명 실패/지연, launch inventory 부족이면 경매를 취소한다. 타임아웃 뒤 누구나 상태를 실패로 고정하고 각자 전액 환불할 수 있어야 한다. 창작자가 판매대금을 임의 회수하거나 운영자가 정산을 무한정 지연해 자금을 묶을 수 없어야 한다. 청구 기한과 미청구 권리의 처리 역시 입찰 전에 고정하며, 운영자가 임의로 참가자의 권리를 몰수하지 못하게 한다.

## 4. 경제 사례 — 비싼 입찰과 싼 입찰의 실제 결과

모든 예시는 결제 토큰/출시 토큰이 정수이며 수수료 0, 공개 최저가격 `2`를 가정한다. `예치 = 최대입찰가 × 희망수량`으로 계산해 설명하지만, 이것을 그대로 **공개 예치액**으로 구현하면 비공개성이 약해진다. 실제 MVP에서는 위의 공통 lot 또는 검증된 shielded 예치가 필요하다.

### 사례 A — 높은 입찰은 전량, 경계 단가 둘은 비례 배정, 싼 입찰은 탈락

판매량 `1,000`. A는 `400개×최대6`, B와 C는 각각 `400개×최대5`, D는 `200개×최대3`을 입찰한다. A에게 400개를 배정하고, 남은 600개를 같은 경계가격의 B·C가 300개씩 나눈다. **청산가격은 5**다.

| 입찰자 | 최대 단가 | 희망량 | 예치 | 배정 | 실제 지급 `5×배정` | 환불 |
|---|---:|---:|---:|---:|---:|---:|
| A | 6 | 400 | 2,400 | 400 | 2,000 | 400 |
| B | 5 | 400 | 2,000 | 300 | 1,500 | 500 |
| C | 5 | 400 | 2,000 | 300 | 1,500 | 500 |
| D | 3 | 200 | 600 | 0 | 0 | 600 |
| **합계** |  |  | **7,000** | **1,000** | **5,000** | **2,000** |

비싸게 `6`을 낸 A도 `6`을 내지 않는다. 싼 `3`을 낸 D는 토큰을 받지 않으며 돈을 모두 돌려받는다. B·C의 제출 순서는 결과에 영향을 주지 않는다.

### 사례 B — 비싼 소량 입찰과 싼 대량 입찰

판매량 `1,000`. A는 `100개×최대6`, B는 `900개×최대4`, C는 `900개×최대3`이다. A 100개와 B 900개가 판매량을 모두 채운다. **청산가격 4**로 A의 실제 지급은 400·환불은 200, B의 실제 지급은 3,600·환불은 0, C의 환불은 2,700이다. 높은 단가 자체가 대량 물량을 강제하지 않는다. 다만 한 사람이 B처럼 공급의 90%를 가져가는 것을 허용할지 `q_cap`과 자격 증명 정책에서 결정해야 한다.

### 사례 C — 같은 가격에 몰린 초과수요

판매량 `1,000`. A·B가 각각 `700개×최대4`를 예치했다. **청산가격 4**, 각 500개 배정·2,000 지급·800 환불이다. 더 먼저 트랜잭션을 보낸 사람이 700개를 독식하지 않는다.

### 사례 D — 공급 미달과 최저 성립 조건

판매량 `1,000`, 최저가격 `2`. A는 `200개×최대4`(예치800), B는 `300개×최대2`(예치600)이다. 모두 배정하면 500개만 팔리므로 가격은 `2`, A는 200개·400 지급·400 환불, B는 300개·600 지급·0 환불이다. 미판매 500개의 운명을 창작자가 사후 선택해서는 안 된다. **경매 생성 시 `최소 판매량`·`최소 모금액`·성립 시 잔여 물량의 락업 또는 소각을 고정**한다. 예를 들어 최소 모금액이 1,500이라면 실제 1,000이므로 경매 실패, A·B 모두 전액 환불한다.

### 사례 E — 다른 예외와 공격

| 상황 | 규칙/실패 판정 |
|---|---|
| 모든 입찰이 최저가격 아래 | 접수 시 거절하거나 무효 처리, 전액 반환. 판매 성립 불가 |
| 예치 부족·가격×수량 오버플로 | 입찰 거절, 가격 정렬에 포함 금지 |
| 창작자 한 지갑으로 선입찰 | 창작자·수수료 수취인 지갑의 자격을 제한 가능. 차명 지갑 전체 차단은 증명 불가 |
| 하나의 사람이 여러 지갑으로 `q_cap` 우회 | 지갑 한도만으로 방지 불가. 신뢰된 중복 방지 자격 발급 필요 |
| 운영자가 불리한 입찰을 누락 | 전체 commitment 수·루트와 정산 입력 일치 증명이 없으면 결과 무효 |
| 입찰자가 마감 뒤 opening 제공을 거부 | MVP는 전체 정산 취소·전액 환불. 한 사람이 전체 경매를 취소시킬 수 있으므로 실제 운영 전 해결 필요 |
| 입찰 도중 취소·수정 | MVP는 `경매당 1개 활성 입찰`로 고정. 취소/수정 허용 시 nonce·보증금·이전 commitment 무효화 규칙 필요. 마감 후 변경 금지 |
| 정산 후 낙찰자가 청구하지 않음 | 자금/토큰을 영구 잠그지 않도록 청구 기한과 보존·회수 정책이 필요. 운영자가 임의로 낙찰자의 권리를 몰수하지 않음 |
| 첫 공개 커브 거래가 몰림 | 경매의 동등한 가격 규칙은 커브 오픈 직후의 순서 경쟁까지 자동으로 해결하지 않음. 개장 시각, 슬리피지 제한, 선택적 추가 일괄 구간 필요 |

## 5. 후속 확장: 본딩커브 연결 — `p_clear`는 숫자 표시만이 아니다

**이 절은 제품 비전의 경제 검산이며 2026 해커톤 MVP의 기능·합격선이 아니다.** 첫 공개 커브 거래의 순서 경쟁도 경매의 공정성 보장을 그대로 이어받지 못한다. 실제 준비금과 매수·매도, 첫 거래 순서 문제를 검증하기 전에는 `경매 후 거래 가능`, `MEV 제거`, `실제 커브 출시`라고 홍보하지 않는다.

가장 단순한 실제 거래 가능한 형태는 Pump처럼 **상수곱 준비금 기반 커브**다. 시작 풀의 판매 토큰 준비금 `X`와 결제 자산 준비금 `Y`라면 수수료를 제외한 첫 현물가격은 `P0 = Y/X`다. 경매 청산가격 `p_clear`와 일치시키려면 `Y = p_clear·X`의 **실제 준비금**이 있어야 한다. 가상 준비금만 맞추고 매도 지급 능력을 입증하지 않은 커브는 사용하지 않는다.

예: 사례 A의 판매대금 5,000 전액과 사전 고정된 커브 재고 1,000 토큰을 넣으면 `X=1,000`, `Y=5,000`, 첫 현물가격은 `5`다. 이어서 사용자가 결제 자산 500을 매수하면, 상수곱 `k=5,000,000` 기준 수령량은 `1,000 − 5,000,000/5,500 ≈ 90.909` 토큰, 평균 매수가격은 약 `5.50`, 거래 후 현물가격은 약 `6.05`다(수수료·반올림 전). 따라서 `첫 가격=5`라고 해서 큰 매수가 모두 5에 체결되는 것은 아니다.

경매가 충분히 팔리지 않으면 `Y`가 적어 약속한 `X`를 같은 가격에 뒷받침하지 못한다. 정해진 최소 성립 기준 미달 시 **커브를 열지 않고 환불**하는 것이 가장 안전하다. 성립했으나 미판매 물량이 있을 경우 `X = Y/p_clear`에 맞춰 사용 재고와 미사용 토큰 처리(소각/장기 락)를 처음부터 고정한다. 커브가 완판되어 DEX 유동성으로 옮겨가는 단계까지 약속한다면 해당 풀과 LP 락이 실제 존재해야 한다. STONK의 위험 문서가 가격 산출·풀 자산·외부 검산이 안 맞으면 초기화를 중단하도록 한 이유도 여기에 있다. [STONK 문서](https://www.stonk.fund/docs/economic-risk/)

## 6. 팁 우선권 경매 — 사용자 제안의 별도 버전

`tip_i` 내림차순으로 일괄 순서를 고정하고 동일한 토큰 묶음 `q`를 커브상에서 **가상으로 순차 매수**시킨다고 가정하자. 슬롯 `j`의 수수료 전 커브 원가가 `C_j`라면 입찰자 총부담은 `C_j + tip_i`다. 경매 종료 후 낙찰자들이 각자 일반 거래를 따로 보내게 하면 다시 거래 포함 속도와 번들이 순서를 바꾸므로, 순차 커브 계산 자체를 정산 증명/계약 실행에 포함해야 한다.

| 확정된 슬롯 | 커브 원가 | 낙찰 팁 | 총부담 |
|---|---:|---:|---:|
| 1번 | 100 | 18 | 118 |
| 2번 | 110 | 9 | 119 |
| 3번 | 120 | 0 | 120 |

이 예시에서는 순서 차익 대부분이 팁으로 회수된다. 1번 입찰자가 팁을 25로 높이면 총부담125로 3번보다 비싸지므로 **높은 팁이 수익을 보장하지 않는다**. 팁 수익을 창작자에게 바로 주면 창작자 차명 입찰의 자기 거래 유인이 커진다. 이 모드를 출시한다면 낙찰자만 팁을 내고, 탈락자는 전액 환불받으며, 팁은 창작자가 인출할 수 없는 유동성 준비금/소각 경로에 보내고, 팁 상한과 1인당 배정 한도를 둬야 한다. 그래도 **자본으로 싼 초기 순서를 사는 상품**이다. 이를 `Fair Launch`라고 부르기보다 `Open Priority Launch`라고 부르는 편이 정확하다.

기본 모드에 팁을 섞으면 심사위원에게 `공정 배정`과 `우선권 판매`의 약속이 동시에 보여 메시지가 약해진다. 기본 MVP는 동일가격 봉인 경매, 팁 모드는 별도 제품 실험으로 권고한다.

## 7. Midnight 구현 경계와 검증해야 할 기술 관문

Compact는 토큰 타입/발행, shielded 자산 수령·지급, private witness에 대한 조건 증명을 제공한다. [표준 라이브러리 API](https://docs.midnight.network/compact/standard-library/exports)와 현재 VeilIntent의 민팅·예치·자기 지갑 청구 경험을 출발점으로 삼을 수 있다. **현재 VeilIntent 7회로/7거래는 다수 입찰 정산이나 밈토큰 양쪽 자산 교환의 증거가 아니다.** 계약은 새로 설계하고 실제 체인에서 다시 검증해야 한다.

| 공개 ledger | 비공개 witness/보호된 로컬 상태 | 실제로 확인할 것 |
|---|---|---|
| launch config 해시, 공급 분배, 등록 수/전체 commitment 루트, 마감·정산 기한 | 각 `p_i, q_i, salt`, 권한 비밀, 원래 수취인 | 공개 원시 트랜잭션에 입찰값·입찰자 연결이 새지 않는지 |
| 청산가격, 총 배정량·대금·환불액, 결과 commitment | 개별 배정·환불 opening | 모든 입찰 포함, 정렬/동점, 회계 보존, 판매량 한도 |
| 실제 체인 거래 ID/최종 상태 | 지갑 자체 잔고·청구 비밀 | 최소 두 낙찰자·한 탈락자의 자기 지갑에서 토큰/환불 확인 |

**첫 관문은 기능 구현이 아니라 핵심 증명의 실행 가능성 검증이다.** 고정 4칸에 등록된 commitment 전부를 누락 없이 묶고, 숨긴 단가/수량으로 정렬·경계 비례 배정·보존식을 검증하는 최소 Compact 회로를 컴파일·실행한다. 증명 시간, 증명/트랜잭션 크기, 체인 수용 여부를 기록한다. 이 관문이 실패하면 UI·커브를 붙여도 `검증 가능한 봉인 경매`라고 주장할 수 없으므로 방향과 범위를 재판정한다.

**다음 통합 관문**은 고정 테스트 토큰 하나·최대 4입찰자·정수 가격/수량·결제용 테스트 토큰 하나로 한다. (1) 고정 재고와 각자의 예치·commitment, (2) 사례 A처럼 두 낙찰자와 한 탈락자를 포함한 실제 정산, (3) `claimTokens`·`claimRefund`의 독립 실행과 각 지갑 잔고 확인, (4) 중복 청구·무효 입찰 거절, (5) 정산 실패 시 전액 환불을 **Local Devnet에서** 확인한다. 참가자가 opening을 제공하지 못하는 상태와 정산자 부재의 타임아웃도 실험한다. 브라우저가 이 경로를 연결하지 못하면 정적 재생 화면을 `작동하는 DApp`이라고 쓰지 않는다.

## 8. 해커톤 출품 가치와 범위 판정

| 관점 | 판정 |
|---|---|
| 문제가 한 문장으로 와닿는가 | **강함** — 개발자 선매수·속도/번들 경쟁을 가격 발견·배정의 공정성 문제로 바꿈. 다만 차명 지갑 방지를 완전 보장할 수 없다 |
| Midnight가 핵심인가 | **강함** — 공개 launch rule + 비공개 입찰값 + 검증 가능한 배정/환불 + shielded 청구를 실제 계약에서 묶을 경우. 단순 UI/오프체인 정렬이면 약함 |
| 새로움 | **중간** — Zama는 자기 토큰 FHE 동일가격 경매, Noctis는 비공개 고정가 구간→커브. 이번 범위의 차이는 **새 밈토큰 첫 판매에서 봉인 가격 발견·토큰 지급·환불까지 실제로 완주**하는 제품 흐름이다. 범용 런치패드나 준비금 커브는 구현 후에만 차별점으로 주장 |
| 기존 코드 재사용 | **부분적** — Compact 민트·escrow·claim/복구 패턴은 참고 가능. 다수 구매자·완전성 증명·두 자산 청구는 새 핵심 계약 |
| 제출 시간 내 완성 가능성 | **핵심 계약·CLI 경로 검증 완료, 제출 완성도는 추가 점검 필요** — 4인 정산·두 자산 청구가 Local Devnet에서 통과했다. 브라우저 지갑 거래, 원시 거래 프라이버시 감사, 제출 영상·Deck은 별도 |
| `해커톤용 MVP` 합격선 | 계약 컴파일·테스트, 실제 체인에서 봉인 입찰→전원 포함 정산→두 낙찰자 토큰 청구·부분 환불→두 탈락자 전액 환불은 **통과**. 공개 repo fresh clone, 제출 설명·영상, 브라우저 거래는 아직 이 검증 결과에 포함되지 않음. 커브 거래는 합격선 제외 |

현재 [공식 해커톤 안내](https://www.hackathon.midnightkorea.org/)는 Local Devnet을 허용하지만, 심사는 저장소를 clone/compile하고 설명·README 일치, Midnight 특징의 명확성, 데모 접근성을 확인한다. 따라서 단순 시뮬레이터나 상세 계획만으로 `작동하는 런치패드`라고 주장하면 안 된다. 별도 제출용 자료(Deck Google Slides, 데모 영상, Academy 인증서, Luma 정보)는 기존 VeilIntent 제출 준비와 무관하게 다시 정렬해야 한다.

## 9. 이번 제출의 기본 결정

1. **이번 제품 약속:** `동일가격 Fair Launch`를 기본으로 한다. 팁 우선권은 별도 실험이며 제출 설명에 섞지 않는다.
2. **프라이버시 경계:** 입찰을 공개 관찰자에게만 숨긴다. 첫 MVP의 마감 후 정산 prover/운영자는 opening을 알 수 있다고 표시한다. 운영자에게도 숨기는 것은 후속 연구다.
3. **참여 자격:** MVP는 지갑별 1회로 제한하며 차명 지갑 방지를 주장하지 않는다. 사람당 1회 credential은 후속이다.
4. **성립/복구 기본값:** 시작 전 최소 판매량·모금액, 미달 시 전액 환불, 미판매 재고 락업 또는 소각, 정산·청구 기한을 고정한다. 어떤 값을 쓸지는 구현과 데모 데이터에 맞춰 공개한다.
5. **범위:** 9/28 제출 목표는 토큰 1종·최대 4명·Local Devnet 실제 경로다. 본딩커브는 설계로만 남기고 실제 거래 UI를 가장하지 않는다.

## 10. 외부 평가를 반영한 실행 판정

외부 검토가 지적한 **전체 입찰 누락 방지, 숨긴 값의 정렬, 다수 지갑의 토큰·환불 청구, 커브 개장 후 재발하는 순서 경쟁**을 우선 리스크로 인정한다. `봉인 경매 + 커브`를 동시에 제출 필수 기능으로 두면 검증할 표면이 지나치게 넓다. **4인 봉인 경매의 증명·실제 청구 관문은 2026-09-26 Local Devnet 실행에서 통과했다.** 전체 런치패드의 본딩커브·브라우저 거래와 더 많은 참가자 확장은 여전히 보류한다. 외부 평가의 주관적 점수는 실제 수상 확률이나 개발 성공률로 채택하지 않는다.

최소 데모는 판매량 600, A `최대12·300개`, B `최대10·500개`, C `최대8·400개`다. 정산가격 10이면 A 300개, B 300개, C 0개다. 각자의 예치를 `p_i×q_i`로 **설명할 때만** A 3,600·B 5,000·C 3,200이고, 실제 지급 A/B 각 3,000, 환불 A 600·B 2,000·C 3,200이다. 총예치 11,800 = 지급 6,000 + 환불 5,800. 실제 입찰에서 동일 공개 예치 lot `D`를 택한다면 `D≥5,000`으로 설정해 위 원문을 숨기고, 각자의 환불은 `D−지급액`으로 다시 계산해야 한다. 공개 예치액과 비공개 입찰 약속이 충돌하는지 원시 거래로 확인한다.

**단계별 중단 조건:** (1) 전체 4개 commitment 포함·정산 증명을 체인에 수용시킬 수 없으면 봉인 경매 주장을 중단한다. (2) 결과가 맞아도 실제 토큰/결제 자산의 독립 청구와 잔고 readback이 안 되면 `실제 토큰 판매`라고 주장하지 않는다. (3) 타임아웃 환불이 없으면 누구나 참여 가능한 판매로 공개하지 않는다. 증거 없는 기능을 사이트·README·발표에 올리지 않는다.

## 11. 재검토 질문

### 다른 모델에 요청할 반대 검토

이 제안서를 검토하는 모델에는 다음을 우선 반박하도록 요청한다. (1) 모든 등록 commitment가 누락 없이 처리됐다는 증명을 Compact 회로 크기/블록 한도 안에서 실제로 만들 수 있는가? (2) 고정 공개 예치 lot 또는 shielded 예치가 입찰 가격·수량을 원시 거래에서 얼마나 누설하는가? (3) 낙찰 경계 동점과 정수 반올림을 salt grinding·차명 지갑이 악용할 수 있는가? (4) 정산자가 사라지거나 bidder opening이 모자랄 때 전액 환불이 실제 가능한가? (5) 창작자 선매수 금지, 익명성, 봇 방지 중 어느 주장이 실제 계약 증거보다 넓은가? 후속 커브 설계에 관해서만 청산가격·첫 가격·실제 준비금·매도 지급 가능성을 반박하라. **구현되지 않은 항목을 성공으로 간주하지 말고 치명적 반례와 가장 작은 검증 spike를 제시해 달라.**
